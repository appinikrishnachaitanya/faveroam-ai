# FaveRoam release implementation and verification

Branch: `feat/faveroam-experience`. This extends the existing application; brand,
routes, session capability model and existing account data remain compatible.
`31a35d5` and newer navigation commit `ee3b993` were present before this work.
No deployment or database execution is implied by a local build or Git push.

## Changes

- DBSCAN groups verified returned places using Haversine distance (1,200 m, two
  minimum points). Stable entity IDs are deduplicated; invalid coordinates and
  content-only entities are omitted. A deterministic real medoid minimizes total
  distance to cluster members. Up to three groups rank by venue count, category
  diversity, compactness and stable ID. Density-connected groups can extend
  beyond 1,200 m end-to-end; the UI shows their actual anchor radius. Outliers
  stay in All discoveries. No neighbourhood names, compatibility percentages,
  extra geocoding or additional Qloo calls are introduced.
- Selecting Around [returned venue] fits the map and filters Discover to that
  group's places. Clear selection restores all categories. Map pins open details
  without toggling the map. Tile errors now trigger the schematic fallback even
  after style loading; Try map again recreates only the failed map. Public CARTO
  raster tiles and OpenStreetMap/CARTO attribution require no API key.
- My places includes My Rituals. Verified discovery cards offer Make a ritual.
  Guests can prepare a named weekday/weekly-or-fortnightly draft and are invited
  to sign in to persist it. Authenticated users create, rename/reschedule, mark
  tried, keep, remove (with confirmation), and replace rituals. There are no
  streaks, notifications, check-ins, social profiles or bookings.
- Replacement is a separate Qloo discovery workflow, not an active-Passport
  mutation. It loads the ritual's saved confirmed interests, merges current
  category/geographic requirements, excludes rejected venues, and validates
  returned city/category/entity references. Up to three alternatives are held in
  a server-only proposal for ten minutes. Approval can select only a proposal's
  entity ID, with matching owner and original ritual version. Persisting uses an
  optimistic version check. Other rituals and plans are not changed. What I
  checked reports executed validation/retrieval steps; it does not claim Gemini
  ran or equate one workflow with one HTTP call. Saved context excludes session
  capabilities, account identity and conversation history.
- First Week database read errors are no longer misreported as Choose your stops
  again. Storage setup returns a distinct code; validation failures retain their
  specific messages. Updates require an existing owned week ID. Ongoing weeks
  remain visible while any dated day is upcoming.
- First Week owns its date/build row and a save/download summary above the day
  editors/map. Day and week planners have distinct switches; save-in-flight
  disables place/time mutations. Previously saved venues remain visible in the
  current selection even if absent from freshly returned options.
- Upcoming plans use a calendar badge/content grid and consistent action rows,
  stacking at narrow widths. The city cover explicitly defines its ivory,
  indigo and teal foregrounds. The mobile welcome resets its inherited 430px
  flex basis, which otherwise became height in a column layout. Tune your vibe
  is collapsed by default. Image export has only Share and Download PNG; public
  read-only links remain a separate feature.
- First Week ICS exports validate IANA time zones and dates, escape CR/newlines,
  fold UTF-8 content lines at 75 octets, include venue-specific event UIDs, retain
  the actual activity label, and roll end times into the next date where needed.

## Database setup — single manual reset

The user explicitly approved app data loss and requested one script. Run
**[setup.sql](../db-scripts/setup.sql)** manually in Supabase's SQL Editor. It
recreates all eight app-owned tables plus the preserved destinations catalogue,
indices, grants and RLS policies. Supabase Auth users and existing destination
rows remain. Saved Passports, plans, weeks, profiles, share links, active sessions,
rituals and replacement proposals are reset. No SQL was executed by the agent.
Do not run this script from startup or CI. Start a **New Passport** after the
reset so its session exists in the newly created session table.

- `saved_first_weeks`: authenticated owners can read/delete their own rows;
  verified server writes use the service role.
- `saved_rituals`: authenticated owners can select only public ritual columns;
  private preference context is server-only. Browser insert/update/delete grants
  are absent; authenticated server handlers enforce ownership and version checks.
- `ritual_replacement_proposals`: service role only, no browser policies. One row
  per owner/ritual bounds abandoned proposals. Expired proposals are rejected;
  new searches overwrite them and deleting a ritual cascades only its proposals.
- No fixed city constraint is added. Only new ritual schedule/name/status fields
  receive bounded-value checks.

After running the migration, use an isolated test account to save/reopen/update/
delete a First Week and create/keep/try/replace/remove a ritual. Confirm owner A
cannot access owner B's records. Check sign-out clears private ritual list and
replacement proposals from the UI; signing in reloads the account's records.

Rollback: code can be rolled back independently. A schema reset's deleted data
cannot be restored without an existing database backup; the user accepted this
loss. No Auth tables or destination rows are dropped, and no `CASCADE` table drop
is used. Existing unrelated tables are untouched. The redundant add-on scripts
were removed so `db-scripts/setup.sql` is the sole operator script.

## Common Ground relevance and shared-week coverage

Shared comparison themes are now soft inspiration signals, not compulsory listing
filters. Existing explicit category/geographic constraints are retained. Joint
retrieval keeps up to 12 returned choices per selected category; each individual
profile retains up to eight verified local places per selected physical category.
This fixes the artificial three-joint/one-personal-card bottleneck without repeating
venues or attributing one person's results to the other. Individual queries run
only for the selected place categories, with a shared 60-second deadline. Partial
search failures preserve successful pools and are disclosed. Common Ground offers
Food/Coffee/Culture explicitly even when the initial Passport was content-only.

Explanations name both confirmed profiles and prioritise specific returned themes.
Broad adjective-only output is labelled as a broad association, equal score badges
are removed, and exact tag matches to actual listings are named. Individual
interest-to-place connections are shown only with positive returned contributions
from both profiles; otherwise the UI explicitly describes aggregate evidence.
Live coverage and relevance remain unverified while the proxy is unavailable.

Map investigation: the active inline MapLibre style requests CARTO `light_all`
raster tiles from `a.basemaps.cartocdn.com` and `b.basemaps.cartocdn.com`; no
remote style/glyph request or API key is configured. CSP has no image/connect
restriction blocking those hosts. A direct tile HEAD request through the required
workspace proxy failed connecting to proxy port 8080 before contacting CARTO.
Therefore live tile status remains unverified. Tile errors produce at most one
safe browser warning per map attempt (provider and HTTP status when available),
then show schematic coordinates and a retry action. No provider migration/payment
is introduced.

The previous implicit 3 km Common Ground cutoff around the first Passport card
was removed: the starting selection is Anywhere in this city. Explicit user
anchors/radii and retrieval geography still apply.

Final Common Ground fixture acceptance also passed at 375/390/768/1440. It
resolved/confirmed a fixture partner, rendered the profile-specific explanation
component without relative-score badges, and built the two-person week from the
full returned fixture pools with at least ten selected places. The earlier live
claim remains intentionally open: fixtures do not prove current Qloo relevance.
The final visible-screen navigation run ranged from 51–240 ms at 4x CPU throttle.

## Follow-up: price feedback and evidence presentation

- “Too expensive” now derives a lower price ceiling from the rejected card's
  returned price category, preserves any stricter cap, and removes a conflicting
  minimum. Unknown-price results cannot establish affordability. If retrieval
  fails, the attempted lower-budget settings stay separate from active settings
  and the reply explicitly says no cheaper alternative was verified.
- Personal Common Ground searches no longer inherit the first person's general
  taste tags. Introduction cards use distinct returned IDs; an exhausted pool
  shows a limitation instead of repeating a venue. Personal themes are displayed
  only when present on the chosen listing. This does not establish exclusivity
  or personal compatibility.
- Evidence badges show counts rather than percentages; expanded details show
  source, operation, listing tags and individual positive contributions when
  available. Broad adjectives are removed from curated theme directions. Soft
  theme inspiration explicitly warns that visible leaders may remain unchanged.
- Removed stale drawer branding, corrected positive-favorite wording, and clear
  Ritual selections when their source discovery disappears.
- These are local fixes. Real provider relevance and deployed behavior still
  require acceptance testing; no database changes are needed for this follow-up.

## First tab activation responsiveness

Workspace headings and illustrations no longer replay entrance reveals on tab
activation. Preferences, Insights and planner panels are prepared one at a time
at browser idle priority using interruptible React transitions; account lists and
provider searches are not prefetched. The idle queue cancels when the Passport
changes, a request starts, or the component unmounts. Browsers without idle
callbacks use a cancellable timer. Planner option lists are memoized by card pool
and city rather than rebuilt on every local edit.

A built production app passed the synthetic browser fixture at 375, 390, 768 and
1440 pixels with 4× CPU throttling: navigation-to-next-paint measurements ranged
from 31–140 ms. Workspace reveal animations are explicitly checked. These local
figures exclude real account/provider latency and do not establish Cloud Run
cold-start performance.

## Chat request controls

The composer uses one action slot: Send when idle, Stop while an agent turn is
pending. Stop remains enabled while other request controls are disabled and
aborts the existing request controller. The separate Cancel refinement action is
removed. A deliberate stop clears retry/error UI and gives a brief chat
confirmation. Greetings and informational questions continue to use read-only
routes; sending a message does not imply a recommendation mutation.

The browser regression holds a synthetic turn pending, checks the enabled Stop
button, aborts it, verifies Send returns and confirms displayed card IDs are
unchanged. No provider call is used by that cancellation test.

## Common Ground layout simplification

Comparison setup collapses after results arrive; the returned category cards now
come before supporting analysis. Distance controls, taste evidence, conversation
starters and the shared First Week remain available through labeled expandable
sections. The personal introduction pair stays visible. Smaller illustrations,
neutral surfaces, consistent card spacing and full-width mobile form actions
reduce visual weight without removing comparison, filters, evidence or planning.
